Performance benchmark ​

On 2026-11-20, the same Apple M1 Pro (16 GiB) and headless Chrome 158.0.8127.36 ran all three targets. Each target and workload used three fresh page sessions. Target order rotated between trials.

Shared 100-paragraph document ​

All three pages loaded the same mixed English and Arabic document and edited near the middle. Paper size was 480 × 640 CSS px, margins were 32 px on each side, font size was 16 and zoom was 100%. The body contained 7,699 UTF-16 units before the test lane. Upstream, initial migration and current produced 13, 19 and 19 pages respectively. Each version used its own font resolution and layout pipeline.

On the shared workload, Backspace handler P95 fell from 460.2 ms in the initial migration to 8.3 ms in the current build. Upstream recorded 5.2 ms. In the built-in playgrounds, IME preedit to second rAF P95 was 32.4 ms upstream, 135.1 ms in the initial migration and 31.6 ms in the current build. The current built-in playground’s Backspace handler had a median of 6.6 ms and a P95 of 49.7 ms, showing a wider spread in the slowest samples.

Method and reproduction ​

  • Viewport 1366 × 720, DPR 1. Each trial warmed up one insertion and deletion, then replayed 12 events each for typing, Backspace and Delete and 7 pinyin preedits before committing “你好”. The driver waited for each keyboard dispatch with at least 50 ms between operations and at least 40 ms between Chrome composition updates.
  • Handler duration comes from the input event for typing and preedit and keydown for deletion. Time to the second requestAnimationFrame measures browser scheduling. This run covers automated Chrome composition, with no measurement of hardware key repeat, system candidate windows or display timing.
  • All 18 trials checked event counts, final text and caret positions. Each workload and target contributed 36 events per keyboard metric and 21 preedit events.
